# Ollama Qwen3.6-35B Investigation - Solution

**Date:** 2026-04-24

This document describes the final solution architecture and all configuration changes made.

---

## The Actual Fix: Streaming Buffer Bug

> **This was the bug that ultimately solved the "random stopping" problem.** Everything else in this investigation — the compat fixes, the thinking mode analysis, the template overrides — were necessary prerequisites to reach this point, but the model was still producing empty responses even after all of those were resolved. The reason: **the custom extension's streaming parser was silently dropping the final chunk of every response.**

### The Bug

The extension reads Ollama's streaming response as JSON lines. Standard streaming parsers accumulate data in a buffer and split on `\n`:

```typescript
// BUGGY VERSION
while (true) {
    const { done, value } = await reader.read();
    if (done) break;  // ← EXITS IMMEDIATELY, buffer is never processed

    buffer += decoder.decode(value, { stream: true });
    const lines = buffer.split("\n");
    buffer = lines.pop() || "";  // Keep incomplete last line in buffer

    for (const line of lines) {
        // Parse and emit events...
    }
}
```

When the reader signals `done: true`, the loop breaks **before processing whatever remains in `buffer`**. If the last chunk from Ollama doesn't end with `\n` (which is common), its content sits in the buffer and is never parsed.

### What This Caused

Ollama's native `/api/chat` streaming sends responses as JSON lines like:

```jsonl
{"message":{"content":"Here is "},"done":false}
{"message":{"content":"the summary."},"done":false}
{"message":{"content":""},"done":true,"prompt_eval_count":8943,"eval_count":67}
```

If the final line (the `done: true` line with usage stats) lacked a trailing newline, the parser never saw it. Worse: for **short responses**, Ollama might send the entire content AND the done signal in a single final chunk — meaning the **entire response content was dropped**.

This explains the session log mystery:
```
[assistant] stop=stop, usage.output=67, content=[]
```
67 tokens were generated by the model, but zero content appeared. The tokens were in the last chunk, the chunk was in the buffer, and the buffer was never processed.

### The Fix

```typescript
// FIXED VERSION
while (true) {
    const { done, value } = await reader.read();
    if (!done) {
        buffer += decoder.decode(value, { stream: true });
    } else {
        buffer += decoder.decode();  // Flush the decoder
    }

    const lines = buffer.split("\n");
    buffer = done ? "" : (lines.pop() || "");  // When done, process ALL lines

    for (const line of lines) {
        // Parse and emit events...
    }

    if (done) break;  // Break AFTER processing, not before
}
```

Three changes:
1. When `done`, flush the TextDecoder with `decoder.decode()` (no args) to get any remaining bytes
2. When `done`, don't pop the last line — process everything in the buffer
3. Move the `break` to AFTER the processing loop, not before

**Location:** `~/.pi/agent/extensions/ollama-native/index.ts`, the `streamOllamaNative` function.

## Solution Architecture

The solution bypasses Ollama's OpenAI-compatible endpoint (`/v1/chat/completions`) entirely and uses a **custom Pi.dev provider extension** that calls Ollama's native `/api/chat` endpoint directly.

```
Pi.dev Agent Loop
    │
    ▼
Custom Extension (ollama-native)
    │  streamSimple implementation
    │  Converts pi.dev messages → Ollama native format
    │  Sends: think: false, tools, messages
    │
    ▼
Ollama /api/chat (native endpoint)
    │  think: false → no thinking overhead
    │  Tool calls returned as structured objects
    │
    ▼
Qwen3.6-35B (Q4)
```

### Why Not the OpenAI-Compatible Endpoint?

The `/v1/chat/completions` endpoint has an irreconcilable problem: it **auto-enables thinking** for Qwen3 models and provides **no client-side mechanism to disable it**. The `think`, `enable_thinking`, and `chat_template_kwargs` parameters are all ignored. This causes 300-800+ tokens of thinking overhead per turn and occasional empty responses when the model "thinks itself into a corner."

The native `/api/chat` endpoint properly supports `"think": false` and reliably produces clean, direct responses.

## All File Changes

### 1. Custom Provider Extension (contains the critical buffer fix)

**Location:** `~/.pi/agent/extensions/ollama-native/index.ts`

**What it does:**
- Registers a new Pi.dev provider called `ollama-native` with API type `ollama-native-api`
- Implements `streamSimple` to handle Ollama's native streaming format
- Converts Pi.dev messages (user/assistant/toolResult) to Ollama's message format
- Converts Pi.dev tool definitions to Ollama's tool format
- Always sends `think: false` to disable thinking
- Parses streaming JSON lines and emits proper Pi.dev stream events:
  - `text_start` / `text_delta` / `text_end` for text content
  - `toolcall_start` / `toolcall_delta` / `toolcall_end` for tool calls
  - `done` / `error` for completion
- Detects tool calls from response structure (not `done_reason`, which is always `"stop"`)
- Sets `stopReason: "toolUse"` when tool calls are present, so Pi.dev continues the agent loop

**Key design decisions:**
- `reasoning: false` on the model config — Pi.dev doesn't manage thinking
- `think: false` on every request — Ollama natively disables thinking
- Tool call arguments from Ollama are already parsed objects (not JSON strings like OpenAI)
- `done_reason` is always `"stop"` in Ollama, even with tool calls — we detect tool calls from `message.tool_calls` presence

### 2. Ollama Modelfile

**Location:** `~/.ollama_local_models/Modelfile.qwen36`

**Final content:**
```
FROM batiai/qwen3.6-35b:q4

PARAMETER num_ctx 131072
PARAMETER num_predict -1
PARAMETER stop <|im_end|>
PARAMETER stop <|endoftext|>
PARAMETER temperature 0.7
PARAMETER top_k 20
PARAMETER top_p 0.95
```

**Changes from original:**
- Removed `PARAMETER stop <|im_start|>` — prevented premature stops in thinking content
- Added `PARAMETER num_predict -1` — ensures no implicit generation cap
- Template is inherited from base model (no override)

**Rebuild command:**
```bash
ollama create qwen3.6-35b-fixed -f ~/.ollama_local_models/Modelfile.qwen36
```

**Location:** `~/.pi/agent/models.json`

The custom extension registers its own model, so no entry is needed in `models.json` for the native provider. However, the existing OpenAI-compat entry remains as a fallback with full compat overrides:

## Remaining Known Issues

### Model Quality (Q4 Quantization)

The Qwen3.6-35B at Q4 quantization occasionally exhibits quality issues that are **not** configuration problems:

- **Wrong parameter names:** Model sends `directory_path` when tool expects `dirpath` (recovers on retry after error)
- **Hallucinated tool names:** Model invents tools that don't exist
- **Wrong agent names:** Uses `"default"` when available agents are `planner`, `reviewer`, `scout`, `worker`

These are inherent to the Q4 quantization level and the model's instruction-following capability. Potential mitigations:
- Lower temperature (0.3-0.5 instead of 0.7) for more deterministic tool calling
- Use a higher quantization (Q5, Q6, Q8) if VRAM permits
- Try the 27b variant which fits more fully in VRAM

## Debugging Tools Created

### Reverse Proxy Logger

**Location:** `~/.ollama_local_models/proxy.py`

A Python reverse proxy that logs request/response metadata between Pi.dev and Ollama. Useful for future debugging.

**Usage:**
```bash
# Start proxy on port 8877, forwarding to Ollama on 11434
python3 ~/.ollama_local_models/proxy.py 8877

# Temporarily change models.json baseUrl to http://127.0.0.1:8877/v1
# Logs are written to /tmp/ollama-proxy.log
```

**What it logs per request:**
- Model, stream mode, tool count, message count
- Message roles array
- All thinking/reasoning-related parameters
- max_tokens / max_completion_tokens
- stream_options, store, extra keys

## Summary of Root Causes (Ordered by Impact)

| # | Issue | Impact | Fix | Was this the fix? |
|---|-------|--------|-----|-------------------|
| **6** | **Streaming buffer bug in extension** | **Last chunk silently dropped — entire content lost for short responses** | **Process remaining buffer before breaking from read loop** | **YES — this was the actual fix** |
| 2 | `/v1/chat/completions` can't disable thinking | 300-800 token overhead per turn, occasional empty responses | Use native `/api/chat` with `think: false` via custom extension | Prerequisite — necessary architectural decision |
| 1 | `supportsDeveloperRole` → system prompt dropped | Tool definitions lost, no tool calls possible | `compat.supportsDeveloperRole: false` | Prerequisite — needed for OpenAI-compat path |
| 3 | `<\|im_start\|>` as stop token | Premature generation stops | Removed from Modelfile | Minor — reduced one failure mode |
| 4 | No `num_predict` set | Potential implicit generation cap | Set `num_predict -1` | Minor — safety net |
| 5 | Unsupported params sent to Ollama | Noise; Ollama ignores them | Compat overrides in models.json | Hygiene — no functional impact |
