# Pi.dev Permission System — Analysis & Roadmap

> Verbose analysis of the current state of the `pi-permissions` extension at `~/.pi/agent/extensions/permissions/`, what it does well, where it falls short, and a prioritized set of improvements inspired by Claude Code / Claw Code's permission model.
>
> Companion reference: `Clients/Personal/AgentNotes/Reference/Claw Code Architecture/06 - Permission & Policy Engine.md`.

---

## 0. TL;DR

The permission extension is **structurally healthy** — well-factored modules, sensible storage, file-watched caches, MCP discovery, and a hard floor on dangerous bash commands.

Tier 1 (R1-R5) is fully complete as of 2026-05-29. R8 (rich /permissions UI) and R9 (audit log) completed same day. The system now has uniform grant shapes, explicit subject prompts, deny/ask rules, a workspace boundary, correct sessionAllow behaviour, bashDefaultLevel naming, a full `/permissions` CLI (list/remove/add/test/log), and JSONL audit logging.

Next priority: **R6** (generic tool registry — closes the coverage gap for unchecked tools like ast_grep_replace and fetch_content).

## 1. Architecture as it stands

### 1.1 Where it lives

- Source: `~/.pi/agent/extensions/permissions/src/`
- Compiled: `~/.pi/agent/extensions/permissions/dist/`
- Global config: `~/.pi/agent/permissions.json`
- Project config: `<project-root>/.pi/permissions.json`
- Loaded automatically by pi-coding-agent because `~/.pi/agent/extensions/` is the auto-discovery path and `package.json` declares the extension entry under `pi.extensions`.

### 1.2 File responsibilities

| File | Lines | Purpose |
|---|---|---|
| `index.ts` | ~850 | Extension entry, hook registration, generic tool handler w/ audit, `/permissions` slash command (show/list/remove/test/add/log/reset/allow-session) |
| `audit.ts` | ~65 | Audit logging — append JSONL to `.pi/permissions-log.jsonl` |
| `evaluation.ts` | ~500 | The decision pipeline — `evaluatePermission(operation, context)` |
| `prompts.ts` | ~470 | Building the prompt message, presenting choices, custom select w/ inline edit for Cancel, `createGrant()` |
| `classification.ts` | ~500 | Shell-command classification into `minimal`/`low`/`medium`/`high` + danger detection |
| `storage.ts` | ~280 | Read/write/cache global + project JSON, file watcher invalidation |
| `sensitive-files.ts` | ~230 | Glob match against the sensitive pattern list (`.env`, `.ssh/*`, `*.pem`, etc.) |
| `project-detection.ts` | ~80 | Walk up from cwd to find the project root |
| `types.ts` | ~125 | All shared types: `Operation`, `Grant`, `PermissionContext`, levels |

### 1.3 Tool coverage

The extension subscribes to `tool_call` and intercepts a closed set:

```ts
if (event.toolName === "bash") …
if (event.toolName === "read") …
if (event.toolName === "write") …
if (event.toolName === "edit") …
if (event.toolName === "mcp") …
if (parseMcpToolName(event.toolName, state.mcpServerNames)) …
// Other tools pass through
```

Anything not in this list — `web_search`, `fetch_content`, `ast_grep_search`, `ast_grep_replace`, `lsp_navigation` (including `rename`), `subagent`, `get_search_content` — receives **no permission check at all**. This is a coverage gap, not a configuration choice.

### 1.4 Grant types

```ts
export type GrantType  = "level" | "operation" | "file-pattern";
export type GrantScope = "once" | "project" | "global";

export interface Grant {
  type: GrantType;
  scope: GrantScope;
  value: string;        // "medium", "bash:npm-install", "read:src/**", "mcp:server:tool"
  grantedAt: number;
}
```

The `value` string flattens a structured idea — `(operation-type, subject-matcher, subject)` — into a single field with different conventions per `type`. This makes the matcher logic in `grantMatches()` non-uniform and hard to extend.

### 1.5 Evaluation pipeline

From `evaluation.ts → evaluatePermission()`:

```
0. context.sessionAllow ?
     bash: classify; dangerous → prompt
     non-bash: allow

1. operation.type === "bash":
     classify(command)
     dangerous → prompt (hard floor)
     scan command string for sensitive paths (find/grep keyword scan + path extraction)
     hits → prompt (unless project allow-list)

2. operation.type === "read":
     sensitive-file glob match → prompt (unless project allow-list)

3. (Removed by us) once-grants in-memory cache

4. project grants → match? allow
   project default level (bash only) → covers level? allow

5. global grants → match? allow

6. global default level (bash only) → covers level? allow

7. fallthrough → prompt
```

Observations:

- **The danger check at step 1 cannot be bypassed** by any grant. Good.
- **Levels are checked only when `classification` is defined**, i.e. bash only. Steps 4/6's "default level" branches are dead code for reads/writes/edits/MCP.
- **No deny step exists**. Order is allow-or-prompt only.
- **`sessionAllow` is broader than it looks** — it short-circuits *before* the sensitive-file check at step 2. So `/permissions allow-session` will silently authorize reading `.env` and `.pem` files; only bash-dangerous remains protected. (Worth fixing — see R4 below.)

### 1.6 Prompt UI

When a prompt fires, the user sees a select like:

```
Run command: npm install express
Classification: Medium

[ Allow once ]
[ Allow for this project ]
[ Allow globally ]
[ Cancel ]
```

Cancel supports inline edit (TAB) to send a redirect message back to the model. The grant the system *records* on "project" / "global" is built by `createGrant()`:

```ts
if (operation.type === "bash" && classification) {
  grant.type = "level";
  grant.value = classification.level;            // ← level-wide!
} else if (operation.type === "read") {
  const dirPath = path.dirname(operation.details);
  grant.type = "file-pattern";
  grant.value = `read:${dirPath}/**`;            // ← folder-wide!
} else {
  grant.type = "operation";
  grant.value = `${operation.type}:${operation.details}`;  // ← file-exact
}
```

The UI text is identical ("Allow for this project") regardless of which branch fires — but the semantics diverge wildly. This is the central UX bug.

### 1.7 Once-grants (after recent fix)

Previously, the `once` scope pushed a grant into `state.context.onceGrants` *after* the prompt resolved, then the *next* matching evaluation consumed it. Net effect: one prompt authorized two tool calls (the original + one cached). We removed the caching entirely; `once` is now truly one-shot. Trade-off: parallel/batched tool calls within the same assistant turn re-prompt N times. Mitigation deferred — see R10.

## 2. What it does well

### 2.1 Module separation

The code reads as if it grew incrementally without becoming a ball of mud. `evaluation.ts` doesn't know about UI; `prompts.ts` doesn't touch disk; `storage.ts` handles cache invalidation in one place. This will make every refactor below easier.

### 2.2 Unbypassable danger floor

Dangerous bash commands (`rm -rf /`, `dd`, `mkfs`, fork bombs, sudo-shell tricks…) are matched in `classification.ts` and short-circuit at step 1 of the pipeline. Even `defaultLevel: "bypassed"` or a `sessionAllow` toggle still prompts. This is the right architectural choice — security floor is independent of policy.

### 2.3 Sensitive-file allowlist is centralized

The pattern list in `~/.pi/agent/permissions.json → sensitiveFilePatterns` is a single source of truth, used both for direct reads and as a target list for the bash-command path scanner. Adding new patterns is one line.

### 2.4 Per-project file is repo-shareable

`<root>/.pi/permissions.json` is plain JSON and small. A team can commit it. Tooling can edit it. The format is forward-compatible — new fields can be added without breaking older readers (they ignore unknown keys).

### 2.5 File-watcher cache invalidation

`storage.ts` keeps an in-memory cache and uses `fs.watch()` to invalidate on change. This means hand-edits to the JSON take effect mid-session, without restart. Nice quality-of-life touch and not at all obvious you'd need it until you don't have it.

### 2.6 MCP server auto-discovery

`loadMcpServerNames()` reads the MCP config file directly and uses its server names to recognize tool-name prefixes (e.g. `obsidian_read_note` → MCP). This means adding a new MCP server is automatically gated without extension-code changes.

### 2.7 Cancel-with-redirect

`promptForPermission()` returns a `cancel-with-message` variant that flows back through `pi.sendUserMessage(..., { deliverAs: "steer" })`. In practice this means refusing an operation can also tell the agent *why*, in the same keystroke flow. Without it, refusal is silent and the model often retries the same thing.

### 2.8 Session-level escape hatch

`/permissions allow-session` exists. Hard to overstate how much friction this removes during exploratory or trusted work, especially compared to permanent grants you'd then have to clean up.

## 3. What's weak

Ordered by impact, biggest first.

### 3.1 (A) Tool coverage is hard-coded

The `tool_call` handler explicitly lists `bash | read | write | edit | mcp`. Every other tool the agent can call is unchecked. This includes:

- `ast_grep_replace` — can rewrite arbitrary code by pattern across whole directories
- `lsp_navigation rename` — can do project-wide identifier rename via LSP edits
- `fetch_content` — performs outbound HTTP, can be steered to internal endpoints
- `web_search` — same exfiltration concern, plus arbitrary URL fetches when `includeContent` is true
- `subagent` — delegates to another agent which is itself unconstrained at this layer

Claude / Claw Code inverts this: every tool *declares* a `required_permission` in its `ToolSpec`, and the enforcer reads that registry. Adding a tool **forces** a permission decision at registration time. Pi's design **forgets** tools.

### 3.2 (B) Grant semantics are inconsistent per tool type

Summarized in §1.6 but worth restating. The same UI choice produces wildly different blast radii:

| Op type | What "Allow for this project" means |
|---|---|
| `bash` (medium-level command, e.g. `npm install express`) | Any future command classified `medium` in this project is auto-allowed |
| `read /home/me/proj/src/foo.ts` | All `read` operations on `src/**` are auto-allowed |
| `edit /home/me/proj/src/foo.ts` | Only that one path is auto-allowed; the next file in the same dir re-prompts |
| `mcp obsidian_read_note` | The MCP tool is auto-allowed for any input |

Three of these four are surprising in opposite directions: bash and read are far broader than the user would guess; edit is far narrower (causing prompt fatigue when the agent edits 5 files in `src/`).

### 3.3 (C) Bash matching by `includes()`

In `grantMatches()`:

```ts
if (operation.type === "bash") {
  return operation.details.toLowerCase().includes(opValue.toLowerCase());
}
```

This is gated behind a `grant.type === "operation"` check, and `createGrant()` currently doesn't produce operation-typed bash grants — so it's dead in practice. But it lurks. If anyone hand-edits the JSON to add a `bash:git` operation grant, **every command containing the substring `git` anywhere — including `rm -rf && git --version` — matches**. Claude Code's rule strings (`bash(git status)` exact, `bash(git:*)` prefix) avoid this by being explicit about the matcher.

### 3.4 (D) No deny / no ask

Only allow-grants exist. You cannot express:

- **Deny**: "In this repo, `git push --force` is never allowed, full stop."
- **Ask**: "`curl` is allowed by my level, but I want a confirmation every single time anyway."

Claude / Claw Code has all three lists with `deny > ask > allow` precedence. Deny rules cannot be overridden by hooks, allow rules, or modes. Ask rules force prompting even when an allow rule matches. This three-tier model is a small amount of code and a large amount of expressive power; the lack of it is the most-felt gap when configuring policy for a specific repo.

### 3.5 (E) Permission "levels" are dressed up as system-wide

`/permissions show` and the README both prominently display:

```
Global default level: Minimal
```

A reasonable reader assumes this controls how much the agent can do across the board. It does not. `LEVEL_INDEX` is consulted only in two places, both gated by `classification` being defined — i.e. only for `bash`. Reads, writes, edits, MCP calls completely ignore the level. This is the single most confusing thing about the system: the headline knob doesn't do what its name suggests for ~80% of tool calls.

### 3.6 Smaller issues

| # | Issue | Notes |
|---|---|---|
| F | **No workspace boundary**. Writes/edits outside `projectRoot` get the same treatment as inside. CC's `WorkspaceWrite` mode auto-confines writes to the project root and forces prompts for anything outside. | Cheap to add |
| G | **Bash sensitive-path detection is regex + token split**. `extractPathsFromCommand()` splits on whitespace and strips quotes by hand. Easy to bypass: `cat /etc/passw"d"` is not flagged. CC walks the tree-sitter AST instead. | Use `bash-parser` or `tree-sitter-bash` |
| H | **No hook override slot**. Other extensions can't cleanly say "this is fine" or "never". They'd compete for the same `tool_call` slot. CC has `PermissionContext.override_decision` populated by hooks before evaluation. | Add an event the extension consumes |
| I | ~~`/permissions` UI is minimal~~ — FIXED by R8. Now has show/list/remove/test/add/log/reset/allow-session. | DONE |
| J | **`sessionAllow` skips sensitive-file checks**. Step 0 short-circuits before step 2. Reading `.env` files becomes free during session-allow. | One-line fix: move sensitive checks above step 0 or make step 0 respect them |
| K | **No turn-aware once-grants**. After our recent fix, `once` is strictly one-shot, so a batched 5-file edit in a single turn prompts 5 times. | Tag grants with current turn id |
| L | ~~No audit log~~ — FIXED by R9. JSONL audit log at `.pi/permissions-log.jsonl`, viewable via `/permissions log`. | DONE |
| M | **Sub-agents inherit trust transparently**. A sub-agent's tool calls go through the same hook with the same grants. CC isolates sub-agent enforcement. | Bigger lift |
| N | **MCP grants are tool-wide, not arg-aware**. Can't say `obsidian_read_note` is allowed only under `Personal/**`. The `rawInput` is in scope but not consulted. | Add optional arg matcher to MCP grants |

| P | **`includes()`-based substring matching** for bash is dead today but a footgun once anyone adds operation-typed bash grants by hand. | Replace with explicit matchers |
| Q | **No "trust on first use" for cwd**. Every directory is implicitly trusted. CC's `TrustResolver` allowlists/denies cwd roots. | Optional but a nice safety rail |

## 4. Side-by-side: Claude/Claw Code vs Pi

| Concept | Claude/Claw Code | Pi (today) |
|---|---|---|
| **Modes** | `ReadOnly` < `WorkspaceWrite` < `DangerFullAccess` < `Prompt` < `Allow` (ordered enum) | `minimal`…`bypassed` (5 levels) — applied **only to bash** |
| **Per-tool requirement** | Tool registers `required_permission: PermissionMode` in its `ToolSpec`; enforcer reads a `BTreeMap<tool, mode>` | Hard-coded per tool type in extension code; new tools not gated unless code edited |
| **Rule shape** | `tool(subject)` strings with `Any` / `Exact(s)` / `Prefix(s)` matchers; single parser | Type-tagged grants with bespoke matching per `type` |
| **allow / deny / ask** | All three. `deny > ask > allow`. Deny cannot be overridden. Ask overrides hook-Allow. | Only allow grants. Deny is implicit & limited to dangerous-bash. No ask. |
| **Subject extraction** | One `extract_permission_subject(input_json)` over an ordered key list (`command`, `path`, `file_path`, `url`, `pattern`, …) producing one normalized string | Each handler digs out its own field; no normalization |
| **Hook overrides** | `PermissionContext.override_decision: Option<PermissionOverride>` populated by pre-tool hooks; merged into evaluation | None |
| **Workspace boundary** | `WorkspaceWrite` mode confines writes to project root | No boundary at all |
| **Bash parsing** | Tree-sitter AST + 6-stage validation pipeline (`bash_validation.rs`) | Regex + token split |
| **Sub-agent isolation** | Separate `PermissionEnforcer` for sub-agent dispatch | Shared |
| **Trust on cwd** | `TrustResolver` allowlist + denylist on dirs; "do you trust this folder?" prompt | Every cwd implicitly trusted |
| **Persistence** | Hierarchical config merge across global + project + flags | Two flat JSON files |
| **Audit** | Event stream (`TrustEvent` etc.) | None |

## 5. Recommendations

### Tier 1 — change the mental model, low cost

#### R1. Make grant subject explicit and uniform

Replace the implicit `level` / `file-pattern` / `operation` choice in `createGrant()` with a second user-facing question after they pick scope. Same shape for every tool type.

For file operations:

```
What should this allow?
  ▸ This exact file:       src/foo.ts
    Files in this folder:  src/**
    Anywhere in project:   **/*
```

For bash:

```
What should this allow?
  ▸ This exact command:    npm install express
    This base command:     npm install *
    Anything matching:     npm:*
```

Grant shape becomes uniform:

```ts
interface Grant {
  tool: "bash" | "read" | "write" | "edit" | "mcp" | string;
  matcher: "exact" | "prefix" | "glob";
  subject: string;
  scope: "project" | "global";
  grantedAt: number;
}
```

No more guessing what `value: "medium"` does. Migration: read old format → translate; write new format only.

#### R2. Adopt deny / ask / allow precedence

Extend the project and global JSON schemas:

```json
{
  "deny": [
    { "tool": "bash", "matcher": "prefix", "subject": "git push --force" }
  ],
  "ask": [
    { "tool": "bash", "matcher": "exact", "subject": "rm" }
  ],
  "allow": [ /* existing grants */ ]
}
```

Evaluation order becomes: `deny → ask → existing allow logic → fallthrough prompt`. Even without UI to manage `deny`/`ask`, hand-editing becomes vastly more expressive.

#### R3. Rename `defaultLevel` → `bashDefaultLevel` (or generalize)

Cheapest: rename + update README + update `/permissions show` text. Removes the implication that the level applies to non-bash tools.

More ambitious: every tool registers a required level; the level applies uniformly. This requires opening up `pi-coding-agent`'s tool registration API to extensions, which it doesn't expose cleanly today. Defer.

#### R4. Make `sessionAllow` respect sensitive files

Move the sensitive-file check above the `sessionAllow` short-circuit, or make `sessionAllow` skip it explicitly only when the user opts in. Currently `/permissions allow-session` is a subtle hole through `.env` protection.

### Tier 2 — extensibility & real safety

#### R5. Workspace boundary

In `evaluation.ts`, add a step before the project/global match for `write`/`edit`:

```ts
if ((op.type === "write" || op.type === "edit") && context.projectRoot) {
  const resolved = path.resolve(op.details);
  if (!resolved.startsWith(context.projectRoot + path.sep)) {
    return { decision: "prompt", reason: "Write outside project root" };
  }
}
```

Cheap, prevents whole classes of accidents (e.g. agent edits `~/.bashrc` because it inferred wrongly).

#### R6. Generic tool registry

Replace the hard-coded `if (event.toolName === ...)` chain with a registry:

```ts
pi.registerToolPermission("ast_grep_replace", {
  extractSubject: (input) => (input.paths ?? []).join(","),
  defaultMatcher: "glob",
  description: "AST-based code rewrite",
});
```

Then all coverage gaps from §3.1 disappear: extensions register their tools, and prompt/storage/evaluation logic is shared. This is the **single change that scales the system**.

#### R7. Subject extractor

Mirror CC's `extract_permission_subject`: an ordered list of input keys producing one normalized string per call. Allows the rule language to be uniform across tool types: `ast_grep_replace(src/**)`, `fetch_content(https://github.com/*)`, `lsp_navigation(rename)`, etc.

Default order: `command`, `path`, `file_path`, `filePath`, `url`, `pattern`, `code`, `message`, then raw input as fallback.

### Tier 3 — quality of life

#### R8. Rich `/permissions` slash command

- `/permissions list` — numbered table of all current grants with origin (project vs global) and matcher details
- `/permissions remove <idx|pattern>` — interactive removal
- `/permissions test <command>` — dry-run evaluation; shows which rule matched and why, useful to debug confusion
- `/permissions add <rule>` — append an allow/deny/ask rule from the prompt

All pure UI work on top of the storage layer.

#### R9. Audit log

Append one JSON line per evaluation to `<project-root>/.pi/permissions-log.jsonl`:

```json
{"ts":"2026-05-19T08:42:13Z","op":{"type":"edit","details":"src/foo.ts"},"decision":"allow","reason":"Allowed by project permissions","grant":{"tool":"edit","matcher":"glob","subject":"src/**"}}
```

Rotate at session boundary or on size. Crucial for trust-recovery ("did the agent really run that?") and for understanding behavior over long sessions.

#### R10. Turn-scoped once-grants

Reintroduce in-memory once-grants but tag them with the current assistant turn id. Clear the cache at turn boundary. "Allow once" then means "for this turn, however many parallel calls". Avoids prompt fatigue on batched edits without re-introducing the old over-authorization bug.

Requires the runtime to expose a turn id to extensions — check `ExtensionAPI` for a `turn_start` / `turn_end` event or a `ctx.turnId`.

#### R11. Hook override slot

Expose a small API:

```ts
pi.onPermissionEvaluate((op, ctx) =>
  someCondition ? { override: "deny", reason: "blocked by team policy" } : undefined
);
```

This lets other extensions inject policy without competing for the `tool_call` slot. Mirrors CC's `PermissionContext.override_decision`. Important if you ever want a "team policy" extension or a remote-config extension.

### Tier 4 — nice but optional

#### R12. AST-based bash parsing

Replace `extractPathsFromCommand()` with `bash-parser` (npm) or `tree-sitter-bash` walking. Quote-bypass attacks (`cat /etc/passw"d"`), expansions, here-docs, redirection targets — all become correctly visible. Do this **after R6** so the runtime dependency lands in a stable architecture.

#### R13. Trust-on-first-use for cwd

First time pi starts in a new directory, prompt: "Trust this folder? (allow project-scoped grants here)". Persist allowlist/denylist of dirs. Helps avoid accidentally accumulating grants in a tmp checkout that you forget about.

#### R14. Per-arg MCP rules

Extend MCP grants with optional argument constraints:

```json
{
  "tool": "mcp",
  "matcher": "exact",
  "subject": "obsidian:obsidian_read_note",
  "argConstraints": { "path": "Personal/**" }
}
```

Narrows blast radius for MCP tools that take path-like args.

## 7. Things I'd specifically NOT recommend doing

- **Don't import CC's full mode hierarchy wholesale.** CC's design assumes a tool-spec registry that pi-mono doesn't expose to extensions today. Forcing levels per tool from an extension is awkward — you'd be working around a missing affordance instead of using it.
- **Don't bring in `tree-sitter-bash` until R6 is done.** Bash AST parsing is a real runtime dep. If the underlying tool architecture is going to be reshaped (R6), do that first, then layer the parser in.
- **Don't try to make the permission system enforce sandboxing.** CC's sandbox is OS-level (`unshare` namespaces). That's a different layer; conflating it with policy is how you end up with a half-working sandbox that gives a false sense of safety.

## 8a. Implementation progress

_Last updated: 2026-05-29_

### ✅ Done

#### R1 — Uniform grant shape + explicit subject prompt

**Status:** Implemented and built. `dist/` is live; the new flow is active in this Pi session forward.

**Decisions taken (confirmed with user):**

1. **Level-based bash grants killed entirely.** Project/global bash grants are now always command-specific (`exact` / `prefix`). The level concept survives only as `defaultLevel` (a separate policy knob applied to bash classification), not as a grant type.
2. **No backwards compatibility.** Old-format grants (`{type, value}`) are silently dropped at load time via `filterValidGrants()`. Existing entries in `~/.pi/.pi/permissions.json` (7 old MCP grants) and any other live config become inert and need to be re-granted through the new prompt.
3. **Glob library:** reused the existing `matchesAnyPattern()` from `sensitive-files.ts` — no new dependencies.
4. **`createGrant()` signature changed** — confirmed no external callers in pi-mono.
5. **Strict R1 isolation** — R2/R3/R4/R5/R6 deliberately not touched in this pass.

**New shape:**

```ts
type GrantMatcher = "exact" | "prefix" | "glob";
type GrantScope   = "project" | "global";   // "once" is UI-only, never stored

interface Grant {
  tool: "bash" | "read" | "write" | "edit" | "mcp";
  matcher: GrantMatcher;
  subject: string;
  scope: GrantScope;
  grantedAt: number;
  label?: string;       // optional pretty-print for /permissions list
}
```

**New UX flow:**

1. First select (unchanged): `Allow once / Allow for this project / Allow globally / Cancel`.
2. On `once` → no second prompt; authorizes only the current call (no caching).
3. On `project` or `global` → second select appears asking *what exactly* to allow.

**Per-tool second-prompt options (built by `subjectScopeOptionsFor()` in `prompts.ts`):**

| Tool | Default (narrowest) | Wider option | Widest option |
|---|---|---|---|
| `read` / `write` / `edit` | `This exact file: <path>` | `Files in this folder: <dir>/**` | `Anywhere in project: <root>/**` |
| `bash` | `This exact command: <cmd>` | `This base command: <verb noun> *` (prefix) | `Any "<verb> ..." command` (prefix) |
| `mcp` | `This exact tool: <server:tool>` | `Any tool from "<server>"` | — |

Narrower options are always shown first / highlighted by default. "Cancel" on the second prompt is a *soft* cancel — the current call still goes through (since the user already said "allow"), but no grant is persisted.

**Files touched:**

| File | Change |
|---|---|
| `src/types.ts` | New uniform `Grant` shape; old `GrantType` removed |
| `src/storage.ts` | `filterValidGrants()` shape-validates on load; dedup key updated to `(tool, matcher, subject)`; `hasGrant` / `filterGrantsByTool` helpers refactored |
| `src/evaluation.ts` | New uniform `grantMatches(grant, operation)` — 3 branches on `matcher`, no per-tool special cases. Steps renumbered |

### ✅ Done: R9 — Audit log (2026-05-29)

**New file: `src/audit.ts`** (~65 lines)

- `logAuditEvent(context, operation, decision, outcome, reason?)` — appends one JSONL line per permission decision. Fire-and-forget (errors silently ignored).
- `getLogPath(context)` — project-level `.pi/permissions-log.jsonl` if projectRoot set, else `~/.pi/agent/permissions-log.jsonl`.

**JSONL entry shape:**
```json
{"timestamp":"2026-05-29T13:15:42.123Z","tool":"bash","details":"npm install express","decision":"allow","outcome":"auto","reason":"Allowed by project permissions"}
```

**Outcome values:**
- `auto` — auto-allowed or auto-denied by grants/rules/level
- `no-ui-fallthrough` — no UI available, fell through to allow
- `prompted:once` / `prompted:project` / `prompted:global` / `prompted:cancel` — user was prompted and chose

Logging is called from 4 points inside `handleToolCallGeneric()`: allow-auto, deny-auto, no-ui-fallthrough, and post-prompt.
